# 레슨 표준

모든 레슨은 이 문서를 기준으로 만들고 검수한다. 목표는 **처음 배우는 사람이 이해하고, 며칠 뒤에도 기억하는 것**이다.

2026-11-24에 분량 기준을 낮췄다. 기준 레슨 둘(J6, O3)을 직접 풀어 보니 문제가 너무 많고 서로 비슷해서 지쳤고, 레슨 하나를 쓰는 데 드는 시간과 비용도 컸다. 품질 기준(근거, 명확한 답, 결론 먼저)은 그대로다.

2026-11-25에 순서를 바로잡았다. 분량을 맞추려고 주제의 핵심 내용을 빼면 안 된다. **알아야 할 것이 빠지지 않는 것이 먼저이고, 분량은 그다음이다.** 그래서 알아야 할 것의 목록, 도입부, "실무에서는" 구역을 더했다. 줄일 것은 내용이 아니라 겹치는 설명과 비슷한 문제다. 아직 이 문서와 다른 곳은 끝의 "아직 맞추지 않은 것"에 적었다.

## 1. 레슨 구조: 핵심 질문

레슨은 **핵심 질문**으로 짠다. 레슨을 마친 사람이 보지 않고 답할 수 있어야 하는 질문이다. 설명을 길게 이어 쓰면 읽을 때는 이해한 것 같아도 무엇이 핵심인지 남지 않는다. 그래서 질문을 먼저 정하고, 본문은 그 질문에 답하게 쓴다.

### 알아야 할 것부터 적는다

질문을 정하기 전에 **이 주제에서 학습자가 알아야 할 것을 전부 적는다**(자료 파일의 `covers`). 자바와 스프링으로 웹 서버를 만드는 개발자가 이 주제로 일하거나 면접을 볼 때 알아야 하는 것이 기준이다.

- 항목마다 어디서 다루는지 적는다: 어느 질문, "실무에서는", "더 알아보기", 또는 "다루지 않음: 맡는 레슨"
- "다루지 않음"에는 그것을 맡는 레슨을 적는다. 맡는 레슨이 없으면 이 레슨이 다루거나 로드맵에 레슨을 더한다
- 설계서를 승인받을 때 이 목록으로 빠진 것이 없는지 본다
- 분량을 맞추려고 이 목록의 항목을 빼지 않는다. 넘치면 레슨을 나눈다

### 질문

- 질문의 수는 알아야 할 것에서 나온다. 보통 3~5개다. 주제가 요구하면 6개까지 쓴다. 7개가 필요하면 레슨을 둘로 나눈다
- 질문은 쓰기 전에 정한다. 어느 질문에도 속하지 않는 내용은 "실무에서는"이나 "더 알아보기"에 둔다
- 질문은 앞 질문의 답에서 다음 질문이 나오게 잇는다 (왜 생기나 → 흔한 해결이 왜 안 되나 → 어떻게 고치나 → 언제 무엇을 쓰나)
- 레슨은 페이지를 직접 쓰지 않고 자료 파일(`site/src/content/lesson-pages/<슬러그>.yaml`)의 칸을 채워 만든다. 아래 표의 구역과 순서는 틀(`site/src/components/lesson/LessonPage.astro`)이 정한다. 칸은 `docs/lesson-data-format.md`에 있다
- 기준 레슨: `site/src/content/lesson-pages/jpa-n-plus-1.yaml`. 2026-11-21에 이 구조로 처음 쓴 레슨이다. 2026-11-24에 낮춘 분량 기준으로 처음 쓴 레슨은 `cookie-session-token.yaml`이다(개념 설명 유형). 그 전에 만든 레슨은 예전 구조(7단계)이고 `site/src/pages/lessons/`에 `.astro`로 남아 있다. 다시 쓸 때 이 구조로 바꾼다
- 공통 도구: 모양은 `site/src/styles/core-question.css`, 진행 표시와 스크립트(예측, 확인 문제, 보지 않고 답하기)는 `site/src/components/CoreQuestionKit.astro`, 자료만으로 만드는 위젯은 `site/src/components/lesson/WidgetKit.astro`다

| 구역 | 목적 | 필수 요소 |
| --- | --- | --- |
| 머리 | 무엇을, 왜 배우는지 | 단원, 시간, 선수 레슨, **도입부**, **핵심 질문 목록**(각 질문으로 가는 링크), 전제(버전, 예제 데이터) |
| 먼저 예측해 보기 | 모르는 상태에서 답을 꺼내 보게 한다 | 레슨 전체에서 쓸 코드나 상황 하나와 보기. 정답은 그 답을 설명하는 질문에서 확인한다. 보통 질문 1이고, 어느 질문인지 예측하는 글에 적는다 |
| 질문 1~N | 질문 하나에 답 하나 | 아래 "질문 한 장의 순서" |
| 실무에서는 | 원리를 자바와 스프링의 코드로 옮긴다 | 아래 "실무에서는" |
| 보지 않고 답하기 | 꺼내 보는 연습 | 핵심 질문을 그대로 다시 묻고 "모범 답 보기"로 비교. 면접 모범 답안 |
| 검증 | 신뢰 | 무엇으로 확인했는지 한 줄과 테스트 파일 링크 |

### 질문 한 장의 순서

1. **질문:** 제목(h2)이 곧 질문이다. 위에 "질문 N"을 붙인다
2. **결론:** 질문 바로 아래 결론 상자. 첫 줄은 질문에 대한 답 한 문장, 둘째 줄은 그 답을 받치는 문장 하나. 결론만 읽어도 답이 되어야 한다
3. **근거:** 코드와 그 코드를 돌린 실제 출력, 나가는 SQL, 그림. 처음 예측한 코드를 다시 보여 주고 지금 설명하는 곳을 강조한다
4. **직접 해 보기 (필요할 때만):** 조작 위젯. 직접 눌러 봐야 이해되는 질문에만 둔다. 코드와 실제 출력으로 충분하면 두지 않는다
5. **확인 문제:** 그 장에서 설명한 것만 묻는 문제 1개
6. **다음 질문으로:** 지금 답에서 생기는 다음 궁금증 한 줄

### 도입부

머리에 두는 서너 문장이다(자료 파일의 `intro`). 왜 배우는지 알아야 끝까지 읽는다. 문단마다 하나씩 쓴다.

1. **실무에서 이 주제를 만나는 장면.** 겪을 법한 일로 쓴다 (예: "서버를 두 대로 늘린 날 사용자들의 로그인이 풀려요")
2. **자바와 스프링 개발자에게 무슨 의미인지.** 어디에 쓰이는지, 개발자가 무엇을 정하고 무엇을 고르게 되는지
3. **이 레슨에서 확인할 것.** 무엇을 돌려서 무엇을 보는지

정의로 시작하지 않는다("쿠키란 ~이다"). 정의는 질문 1이 한다.

### 실무에서는

질문이 원리를 답한다면, 이 구역은 그 원리가 **자바와 스프링의 코드에서 어떻게 보이는지**를 답한다(자료 파일의 `practice`). 질문들 뒤, "보지 않고 답하기" 앞에 둔다.

- **실제로 쓰는 코드와 설정을 보여 준다.** 애너테이션, 클래스, `application.yml`, 의존성. 원리를 설명하려고 만든 코드가 아니라 프로젝트에 그대로 들어갈 모양으로 쓴다
- **흔한 실수 하나와 고친 코드를 둔다.** 실수가 왜 생기는지는 앞의 질문에서 배운 원리로 설명한다
- **돌려서 확인한다.** 검증 테스트로 돌려 실제 출력을 붙인다. 프로젝트에 의존성을 더해야 해서 돌리기 어려운 것은 공식 문서를 근거로 적고, 테스트가 아니라 문서가 근거라는 것을 본문에 밝힌다
- 질문에서 한 설명을 되풀이하지 않는다. "질문 2에서 본 것"처럼 가리키고 코드로 넘어간다
- 스프링과 먼 주제(운영체제, 자료구조, 네트워크의 아래 계층)는 억지로 코드를 만들지 않는다. 자바와 스프링 개발자가 이 개념을 만나는 곳(설정값, 로그, 장애 상황)을 짧게 적는다
- 주제 자체가 스프링의 코드인 레슨(JPA, 트랜잭션)은 질문이 이미 코드로 답한다. 이때 이 구역에는 운영에서 만나는 것을 쓴다: 설정, 흔한 실수, 로그에서 알아보는 법

### 분량

레슨 하나는 20분 안팎에 읽는다. 분량은 내용을 빼는 이유가 아니라 **살펴보라는 신호**다.

- 자료 파일의 크기를 잰다(`wc -c`). 설계 때 채운 칸까지 들어간 크기다. 도입부와 실무 구역을 갖춘 기준 레슨 `cookie-session-token.yaml`이 52KB다. 도입부와 실무 구역이 아직 없는 `jpa-n-plus-1.yaml`은 21KB다
- 60KB를 넘으면 두 가지를 본다. 같은 설명을 두 번 했는지, 레슨 둘로 나눌 주제인지. 알아야 할 것을 빼서 줄이지 않는다
- 위젯은 레슨에 1개 이상이면 된다. 질문마다 두지 않는다
- 실제 출력은 "정말 그런가" 싶은 결과에만 붙인다. 뻔한 결과마다 붙이지 않는다
- 같은 것을 표와 글로 두 번 적지 않는다

## 2. 검수 체크리스트

레슨을 올리기 전에 아래를 모두 확인한다.

- [ ] **빠진 것이 없는지:** 알아야 할 것(`covers`)의 항목이 모두 적힌 곳에서 실제로 설명된다. "다루지 않음"에는 맡는 레슨이 적혀 있다
- [ ] **도입부:** 실무에서 만나는 장면, 자바와 스프링 개발자에게 무슨 의미인지, 이 레슨에서 확인할 것이 있다
- [ ] **실무에서는:** 실제로 쓰는 코드나 설정이 있고, 흔한 실수와 고친 코드가 있다. 테스트로 확인했거나 공식 문서를 근거로 달았다
- [ ] **핵심 질문:** 결론 상자의 첫 줄만 이어 읽어도 레슨 요약이 된다. 질문 안에 그 질문에 답하지 않는 문단이 없다
- [ ] **정확성:** 동작에 대한 주장(쿼리 수, SQL 발생 시점, 반영 여부 등)마다 `verification/` 테스트가 있고 CI가 통과한다
- [ ] 테스트로 확인할 수 없는 주장(설계 권장 등)은 공식 문서를 근거로 단다
- [ ] **처음 배우는 사람:** 용어는 처음 나올 때 한 문장으로 설명한다. 선수 개념을 명시한다
- [ ] **모르는 독자로 읽기:** 대상 독자(자바와 SQL 기초만 앎)로 본문을 끝까지 읽고, 설명도 링크도 없는 용어가 남지 않았는지 확인한다. 몰라도 되는 세부는 "더 알아보기"로 접는다 (기준: `docs/reviews/2026-11-16-beginner-review.md`)
- [ ] **앞뒤가 맞는지:** 본문의 숫자와 위젯이 보여 주는 숫자, 문제의 정답이 서로 같다
- [ ] **꺼내 보는 장치:** 시작 전 예측, 질문마다 확인 문제, 보지 않고 답하기가 있다
- [ ] **눈에 보이는 근거:** 질문마다 코드, 실제 출력, 그림, 위젯 가운데 하나가 있다
- [ ] **분량:** 같은 설명을 두 번 하지 않았다. 60KB를 넘으면 1장의 "분량"대로 살펴봤다
- [ ] **문제:** 4장의 개수를 지키고, 같은 것을 다시 묻는 문제가 없다
- [ ] **면접 연결:** 모범 답안이 정의 → 원리 → 트레이드오프 → 경험 순서다
- [ ] **근거:** 출처는 공식 문서와 스펙이다. 책과 강의의 내용은 옮기지 않는다
- [ ] **화면:** 375px 너비에서 가로 스크롤이 없다(코드 블록 포함). 콘솔 오류가 없다. 앱 안 화면(주소 끝에 `?embed=1`)에서도 확인한다

## 3. 글쓰기 규칙

- 해요체, 짧은 문장. 한 문단에 한 가지 생각
- 결론을 먼저 쓴다. 이유와 예시는 그 뒤에 쓴다
- 비유는 한 번만, 그다음은 정확한 용어로 (예: "빈 상자" → 프록시)
- 버전에 따라 달라지는 동작은 버전을 적는다 (예: Hibernate 6.6)
- 확인하지 않은 내용은 단정하지 않는다 ("~하기도 해요")
- "3번"처럼 횟수인지 순서인지 헷갈리는 말은 풀어 쓴다 ("쿼리 3번", "세 번째 단계")
- 정보를 가운뎃점(·)으로 늘어놓지 않는다. 쉼표나 "와"로 잇는다

### 코드

- 한 줄은 44자를 넘기지 않는다. 375px 화면에서 가로로 밀지 않고 읽혀야 한다. 로그처럼 줄일 수 없는 줄은 `prewrap` 블록으로 줄을 바꾼다. 접어 둔 영역(더 알아보기) 안의 코드는 폭이 더 좁아서 40자를 넘기지 않는다
- 자료 파일의 `codes`에 이름을 붙여 두고 본문 블록에서 이름으로 쓴다
- 44자에 맞추려고 끊은 줄은 끝에 `⤶`를 붙인다. 좁은 화면에서만 줄이 바뀌고, 넓은 화면(720px 이상)에서는 다음 줄과 빈칸 하나로 이어져 한 줄로 보인다. 빈칸 없이 이어야 하면 `⤷`를 쓴다. 이은 줄은 84자를 넘기지 않는다. 원래 여러 줄로 쓰는 코드(JPQL 텍스트 블록, 긴 join)에는 붙이지 않는다
- 지금 봐야 할 곳은 코드에서 `[[이렇게]]` 감싸 형광펜으로 강조한다. 한 블록에 한두 곳만 한다
- 강조한 곳이 무엇인지는 코드 주석이 아니라 코드 아래 설명(`notes`)에 쓴다. 주석은 실제 코드에 있을 법한 것만 쓴다
- 본문은 레슨 전체에서 같은 예제 코드로 이어 간다. 문제는 4장대로 다른 예시도 쓴다

### 색 (테마 `soft pastel`, `site/src/styles/retrievo-theme.css`)

색마다 뜻이 하나다. 꾸미려고 다른 색을 더하지 않는다.

- 라벤더: 테마 색. 누를 수 있는 것, 결론, 모범 답, 가져온 데이터
- 산호: 문제. 늘어난 쿼리, 틀림, 잘린 데이터
- 민트: "맞았어요" 판정에만
- 레몬: 코드의 형광펜에만
- 팀 색 네 가지: 행이 어느 팀 것인지 구분해야 하는 표에서만
- Retrievo 앱과 같은 테마다. 밝은 화면만 쓴다

## 4. 문제 규칙 (`content/questions/<slug>.yaml`, 학습 앱 Retrievo가 가져간다)

문제는 적게, 서로 다르게 낸다. 많이 푸는 것보다 며칠 뒤에 다른 모양으로 다시 만나는 것이 기억에 남는다.

### 근거와 답

- **본문이 설명한 원리에 근거가 있어야 한다.** 본문에서 설명하지 않은 것은 묻지 않는다. 묻고 싶으면 본문에 먼저 쓴다
- **근거는 원리이고, 예시는 달라도 된다.** 본문의 예제(클래스 이름, 숫자, 상황)를 그대로 써야 한다는 뜻이 아니다. 본문이 `Member`의 이메일로 설명했으면, 문제는 `Point`의 좌표로 같은 원리를 물을 수 있다
- **답이 명확해야 한다.** 조건(버전, 데이터 수, 설정)을 문제에 적어 정답이 하나로 정해지게 한다. "상황에 따라 다르다"가 답이 될 수 있는 문제는 판정 문제로 내지 않는다
- **해설은 결론 먼저.** 첫 문장을 굵게 쓴 결론으로 시작하고 이유를 잇는다
- 문제의 정답이 동작에 관한 것이면 검증 테스트로 확인한다. 본문과 다른 예시로 낸 문제도 마찬가지다

### 개수

| | 개수 | 내용 |
| --- | --- | --- |
| 판정 문제 | 핵심 질문마다 2개 (많아도 3개), 레슨 전체 6~12개 | 아래 두 가지를 하나씩 |
| 설명형 문제 | 레슨에 1~2개 | 핵심 질문 전체를 잇는 면접 질문 하나는 꼭 둔다 (`coreQuestion: all`) |

핵심 질문마다 판정 문제 둘은 서로 다른 일을 한다.

1. **본문의 예시로 묻는 문제.** 방금 읽은 것을 이해했는지 본다. 배운 날에 푼다. 파일에서 그 질문의 첫 문제로 적는다. 앱은 질문마다 검수가 끝난 첫 판정 문제 하나만 레슨에서 묻는다
2. **다른 상황으로 옮긴 문제.** 예시를 바꿔도 같은 원리로 답할 수 있는지 본다. 며칠 뒤의 재확인에 나간다

- **실무 구역에서도 묻는다.** "실무에서는"에서 설명한 코드는 관련된 핵심 질문에 묶어 판정 문제로 낸다. 레슨에 하나 이상 둔다. 흔한 실수를 코드로 보여 주고 무슨 일이 생기는지 묻는 문제가 좋다. 그 질문의 셋째 문제로 적는다
- **같은 것을 다시 묻지 않는다.** 두 문제의 답을 가르는 지식이 같고 겉모습만 다르면 하나를 지운다. 예시를 옮긴 문제는 숫자만 바꾼 문제가 아니다. 상황이 달라져서 원리를 다시 적용해야 풀리는 문제다
- 질문마다의 설명형 문제는 만들지 않는다. 레슨 페이지의 "보지 않고 답하기"가 그 일을 한다
- 설명형 문제의 체크리스트는 4~5개. 4개 이상 정답 / 2~3개 부분 / 1개 이하 오답
- 판정 문제의 형태: 객관식, OX, 코드 예측, 줄 고르기. 정답이 하나로 정해진다

### 파일

- 문제는 레슨마다 `content/questions/<slug>.yaml` 파일 하나에 둔다. 형식은 [Retrievo의 문제 파일 형식](https://github.com/wanja727/retrievo/blob/main/docs/content-format.md)을 따르고, CI(`Check questions`)가 Retrievo의 검사기로 확인한다
- 파일의 `coreQuestions`에 핵심 질문을 적고(키는 레슨 페이지의 장 id와 같은 `q1`, `q2`), 문제마다 `coreQuestion`으로 어느 질문에서 나왔는지 묶는다. 질문 여럿을 한꺼번에 묻는 문제는 `all`로 적는다. 묶이지 않은 문제가 있으면 CI가 실패한다
- 이 장의 규칙 가운데 기계가 볼 수 있는 것은 같은 CI의 `standard`가 본다(`scripts/check-questions.mjs`): 가운뎃점, 핵심 질문 3~6개, 질문마다 판정 2개 이상, 레슨 전체 판정 6개 이상, 설명형 1개 이상, 해설의 굵은 결론. 개수의 위쪽 한계(질문마다 3개, 레슨 전체 판정 12개, 설명형 2개)를 넘거나 `all`로 묶인 면접 질문이 없으면 경고만 한다. 핵심 질문 구조로 쓴 파일만 검사한다. 올리기 전에 `scripts`에서 `npm run check:questions`로 먼저 돌려 본다
- 본문 단계(`steps`)는 쓰지 않는다. 앱이 레슨 페이지를 앱 안에서 연다
- 새 문제는 `status: draft`로 넣고, 근거를 확인한 뒤 `reviewed`로 바꾼다. Retrievo는 `reviewed`만 보여준다. 문제 키(`key`)는 한 번 정하면 바꾸지 않는다. 뺄 문제는 파일에서 지운다(앱에서 숨겨지고 기록은 남는다)
- 코드 문제(줄 고르기)는 `code`에 줄 번호 없이 코드를 넣고 정답을 줄 번호로 적는다(화면이 번호를 붙인다)

## 5. 기록할 숫자

커밋 메시지에 적는다. 나중에 콘텐츠 비용과 품질을 숫자로 말하기 위해서다.

- 제작 시간, 검수 시간
- 자료 파일의 크기(KB), 판정 문제와 설명형 문제의 수
- 검수에서 고친 사실 오류 수 (테스트 실패로 발견한 것 포함)
- 배포 후: D+7 판정 정답률 → 낮으면 레슨을 고친다

## 6. 위젯

위젯은 직접 눌러 봐야 이해되는 곳에만 둔다. 둘 때는 공통 위젯에서 먼저 고른다. 자료만 적으면 되고, 모든 레슨에서 같은 모양으로 나온다 (`docs/lesson-data-format.md`의 "위젯").

- 지금 있는 것: 상황 분류하기(`classify`), 켜고 끄며 비교하기(`toggle`), 한 단계씩 실행하기(`steps`), 두 칸 비교(`compare`), 타임라인(`timeline`)
- 두 칸 비교는 같은 요구를 두 코드나 두 방식에 넣었을 때 양쪽에서 고쳐야 하는 것, 달라지는 것을 나란히 볼 때 쓴다. 타임라인은 두 쪽이 주고받는 요청과 응답을 차례로 볼 때 쓴다
- 공통 위젯으로 안 되는 것만 레슨 전용으로 만든다. 슬라이더로 값을 바꿔 계산 결과를 보는 것, 누르는 순서가 정해지지 않은 것이 그렇다. 전용 위젯은 레슨에 하나까지만 둔다
- 레슨 전용 위젯과 같은 형태가 **세 번째 레슨에 나오면** 공통 위젯으로 뽑는다

## 7. 실제 결과와 검증

레슨의 결과는 짐작이 아니라 코드를 돌려 확인한 값이다. 그 사실을 본문 안에서 보여 준다.

- **실행한 코드와 실제 출력을 한 상자에 둔다.** 무엇을 돌린 결과인지 위로 올라가 찾지 않게 한다. 출력은 먼저 예측하게 한 뒤에 연다
- 출력은 검증 테스트가 `CiOutput.record(레슨, 이름, 출력)`으로 남긴 값이다. 배포 워크플로가 테스트를 돌려 `/ci/<레슨>.json`으로 올린다. 시간이 나오는 예제는 이 실측값을 쓴다
- Spring과 JPA 예제는 `SqlCapture`가 잡은 실제 Hibernate SQL을 같은 방법으로 보여 준다
- **검증 구역은 한 줄이다.** 무엇으로 확인했는지(예: "자바 21에서 코드를 돌려 확인했어요")와 테스트 파일 링크를 둔다. 상황과 결과를 다시 적은 표, 테스트 코드 한 토막과 그 설명, 저장소에서 돌려 보는 방법은 넣지 않는다. 본문이 이미 보여 준 것을 되풀이하고, 앞뒤 없이 보는 테스트 코드는 읽히지 않는다
- 브라우저 안에서 코드를 돌리는 장치는 쓰지 않는다. 브라우저용 PostgreSQL(PGlite)은 받는 크기에 비해 쓰임이 적어서 뺐고, 브라우저용 JVM(CheerpJ)은 한국에서 로딩이 2분 가까이 걸렸다(`spike/run-in-browser` 브랜치 기록)
