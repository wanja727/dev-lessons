# 레슨 표준

모든 레슨은 이 문서를 기준으로 만들고 검수한다. 목표는 **처음 배우는 사람이 이해하고, 며칠 뒤에도 기억하는 것**이다.

## 1. 레슨 구조: 핵심 질문

레슨은 **핵심 질문 3~5개**로 짠다. 레슨을 마친 사람이 보지 않고 답할 수 있어야 하는 질문이다. 설명을 길게 이어 쓰면 읽을 때는 이해한 것 같아도 무엇이 핵심인지 남지 않는다. 그래서 질문을 먼저 정하고, 본문은 그 질문에 답하는 데 필요한 것만 쓴다.

- 질문은 쓰기 전에 정한다. 질문에 답하는 데 필요 없는 내용은 빼거나 "더 알아보기"로 접는다
- 질문은 앞 질문의 답에서 다음 질문이 나오게 잇는다 (왜 생기나 → 흔한 해결이 왜 안 되나 → 어떻게 고치나 → 언제 무엇을 쓰나)
- 기준 레슨: `site/src/pages/lessons/jpa-n-plus-1.astro`. 2026-11-21에 이 구조로 처음 쓴 레슨이다. 그 전에 만든 레슨은 예전 구조(7단계)이고, 다시 쓸 때 이 구조로 바꾼다
- 공통 도구: 모양은 `site/src/styles/core-question.css`, 진행 표시와 스크립트(예측, 확인 문제, 보지 않고 답하기)는 `site/src/components/CoreQuestionKit.astro`의 `window.Lesson`을 쓴다. 두 번째 레슨 `tx-basics.astro`가 이 도구를 쓰는 예다

| 구역 | 목적 | 필수 요소 |
| --- | --- | --- |
| 머리 | 무엇을 배우는지 | 단원·시간·선수 레슨, **핵심 질문 목록**(각 질문으로 가는 링크), 전제(버전, 예제 데이터) |
| 먼저 예측해 보기 | 모르는 상태에서 답을 꺼내 보게 한다 | 레슨 전체에서 쓸 코드 하나와 보기. 정답은 질문 1에서 확인한다 |
| 질문 1~N | 질문 하나에 답 하나 | 아래 "질문 한 장의 순서" |
| 보지 않고 답하기 | 꺼내 보는 연습 | 핵심 질문을 그대로 다시 묻고 "모범 답 보기"로 비교. 면접 모범 답안 |
| 검증 (접어 둔다) | 신뢰 | 상황과 확인한 결과 표, 테스트 하나를 코드로 보여 주기, `<RunLocally>` |

### 질문 한 장의 순서

1. **질문:** 제목(h2)이 곧 질문이다. 위에 "질문 N"을 붙인다
2. **결론:** 질문 바로 아래 결론 상자. 첫 줄은 질문에 대한 답 한 문장, 둘째 줄은 그 답을 받치는 문장 하나. 결론만 읽어도 답이 되어야 한다
3. **근거:** 코드, 나가는 SQL, 그림. 처음 예측한 코드를 다시 보여 주고 지금 설명하는 곳을 강조한다
4. **직접 해 보기:** 조작 위젯 1개. 결론이 맞는지 숫자나 상태로 확인하게 한다
5. **확인 문제:** 그 장에서 설명한 것만 묻는 문제 1개
6. **다음 질문으로:** 지금 답에서 생기는 다음 궁금증 한 줄

## 2. 검수 체크리스트

PR마다 아래를 모두 확인한다.

- [ ] **핵심 질문:** 결론 상자의 첫 줄만 이어 읽어도 레슨 요약이 된다. 어느 질문에도 답하지 않는 문단이 없다
- [ ] **정확성:** 동작에 대한 주장(쿼리 수, SQL 발생 시점, 반영 여부 등)마다 `verification/` 테스트가 있고 CI가 통과한다
- [ ] 테스트로 확인할 수 없는 주장(설계 권장 등)은 공식 문서를 근거로 단다
- [ ] **처음 배우는 사람:** 용어는 처음 나올 때 한 문장으로 설명한다. 선수 개념을 명시한다
- [ ] **모르는 독자로 읽기:** 대상 독자(자바·SQL 기초만 앎)로 본문을 끝까지 읽고, 설명도 링크도 없는 용어가 남지 않았는지 확인한다. 몰라도 되는 세부는 "더 알아보기"로 접는다 (기준: `docs/reviews/2026-11-16-beginner-review.md`)
- [ ] **앞뒤가 맞는지:** 본문의 숫자와 위젯이 보여 주는 숫자, 문제의 정답이 서로 같다
- [ ] **꺼내 보는 장치:** 시작 전 예측, 질문마다 확인 문제, 보지 않고 답하기가 있다
- [ ] **시각화:** 질문마다 조작 위젯이나 그림이 있다
- [ ] **면접 연결:** 모범 답안이 정의 → 원리 → 트레이드오프 → 경험 순서다
- [ ] **근거:** 출처는 공식 문서·스펙. 책·강의 내용은 옮기지 않는다
- [ ] **화면:** 375px 너비에서 가로 스크롤이 없다(코드 블록 포함). 콘솔 오류가 없다. 앱 안 화면(주소 끝에 `?embed=1`)에서도 확인한다

## 3. 글쓰기 규칙

- 해요체, 짧은 문장. 한 문단에 한 가지 생각
- 결론을 먼저 쓴다. 이유와 예시는 그 뒤에 쓴다
- 비유는 한 번만, 그다음은 정확한 용어로 (예: "빈 상자" → 프록시)
- 버전에 따라 달라지는 동작은 버전을 적는다 (예: Hibernate 6.6)
- 확인하지 않은 내용은 단정하지 않는다 ("~하기도 해요")
- "3번"처럼 횟수인지 순서인지 헷갈리는 말은 풀어 쓴다 ("쿼리 3번", "세 번째 단계")
- 정보를 가운뎃점(·)으로 늘어놓지 않는다. 아이콘과 간격으로 나눈다

### 코드

- 한 줄은 44자를 넘기지 않는다. 375px 화면에서 가로로 밀지 않고 읽혀야 한다. 로그처럼 줄일 수 없는 줄은 `pre.wrap`으로 줄을 바꾼다. 접어 둔 영역(검증, 더 알아보기) 안의 코드는 폭이 더 좁아서 40자를 넘기지 않는다
- 프론트매터에 문자열로 두고 `<pre set:html={highlight(code)} />`로 넣는다 (`site/src/lib/highlight.ts`)
- 44자에 맞추려고 끊은 줄은 끝에 `⤶`를 붙인다. 좁은 화면에서만 줄이 바뀌고, 넓은 화면(720px 이상)에서는 다음 줄과 빈칸 하나로 이어져 한 줄로 보인다. 빈칸 없이 이어야 하면 `⤷`를 쓴다. 이은 줄은 84자를 넘기지 않는다. 원래 여러 줄로 쓰는 코드(JPQL 텍스트 블록, 긴 join)에는 붙이지 않는다
- 지금 봐야 할 곳은 코드에서 `[[이렇게]]` 감싸 형광펜으로 강조한다. 한 블록에 한두 곳만 한다
- 강조한 곳이 무엇인지는 코드 주석이 아니라 코드 아래 설명(`ul.code-note`)에 쓴다. 주석은 실제 코드에 있을 법한 것만 쓴다
- 레슨 전체에서 같은 예제 코드를 쓴다. 문제의 코드도 본문과 같은 모양으로 쓴다

### 색 (테마 `soft pastel`, `site/src/styles/retrievo-theme.css`)

색마다 뜻이 하나다. 꾸미려고 다른 색을 더하지 않는다.

- 라벤더: 테마 색. 누를 수 있는 것, 결론, 모범 답, 가져온 데이터
- 산호: 문제. 늘어난 쿼리, 틀림, 잘린 데이터
- 민트: "맞았어요" 판정에만
- 레몬: 코드의 형광펜에만
- 팀 색 네 가지: 행이 어느 팀 것인지 구분해야 하는 표에서만
- Retrievo 앱과 같은 테마다. 밝은 화면만 쓴다

## 4. 문제 규칙 (`content/questions/<slug>.yaml`, 학습 앱 Retrievo가 가져간다)

- **레슨에 근거가 있어야 한다.** 문제마다 어느 핵심 질문에서 나왔는지 파일에 주석으로 묶어 둔다. 본문에서 설명하지 않은 것은 묻지 않는다. 묻고 싶으면 본문에 먼저 쓴다
- **답이 명확해야 한다.** 조건(버전, 데이터 수, 설정)을 문제에 적어 정답이 하나로 정해지게 한다. "상황에 따라 다르다"가 답이 될 수 있는 문제는 판정 문제로 내지 않는다
- **해설은 결론 먼저.** 첫 문장을 굵게 쓴 결론으로 시작하고 이유를 잇는다
- 핵심 질문마다 판정 2개 이상, 설명형 1개. 레슨 전체로는 **판정 8개 이상 + 설명형 3개 이상**
- 설명형(설명·비교·상황): 정답 토글 안에 체크리스트 4~5개. 4개 이상 정답 / 2~3개 부분 / 1개 이하 오답
- 판정(객관식·OX·코드 예측·줄 고르기): 정답이 하나로 정해진다. D+3·D+7 지연 확인은 판정 문제 중 처음 풀지 않은 것으로 한다
- 문제는 레슨마다 `content/questions/<slug>.yaml` 파일 하나에 둔다. 형식은 [Retrievo의 문제 파일 형식](https://github.com/wanja727/retrievo/blob/main/docs/content-format.md)을 따르고, CI(`Check questions`)가 Retrievo의 검사기로 확인한다
- 본문 단계(`steps`)는 쓰지 않는다. 앱이 레슨 페이지를 앱 안에서 연다
- 새 문제는 `status: draft`로 넣고, 근거를 확인한 뒤 `reviewed`로 바꾼다. Retrievo는 `reviewed`만 보여준다. 문제 키(`key`)는 한 번 정하면 바꾸지 않는다. 뺄 문제는 파일에서 지운다(앱에서 숨겨지고 기록은 남는다)
- 코드 문제(줄 고르기)는 `code`에 줄 번호 없이 코드를 넣고 정답을 줄 번호로 적는다(화면이 번호를 붙인다)
- 문제의 정답이 동작에 관한 것이면 검증 테스트와 같은 시나리오를 쓴다

## 5. 기록할 숫자

PR 설명에 적는다. 나중에 콘텐츠 비용과 품질을 숫자로 말하기 위해서다.

- 제작 시간, 검수 시간
- 검수에서 고친 사실 오류 수 (테스트 실패로 발견한 것 포함)
- 배포 후: D+7 판정 정답률, "확실한데 틀림" 개수 → 낮으면 레슨을 고친다

## 6. 재사용 위젯

같은 형태의 위젯이 **세 번째 레슨에 나오면** 공통 컴포넌트로 뽑는다. 그 전에는 복사해서 쓴다.
현재 후보: SQL 로그와 쿼리 수 표시, 단계 넘기기 도식, 탭 비교, 확인 문제, 면접 답변 비교.

## 7. 실제 결과 보여주기

시뮬레이터 옆에 진짜 결과를 둔다. 자바 동시성 예제는 출력을 먼저 예측하게 한 뒤, 검증 테스트가 `CiOutput.record(레슨, 이름, 출력)`으로 남긴 실제 JVM 출력을 `<CiOutput>`으로 공개한다(시간이 나오는 예제는 이 실측값을 쓴다). Spring·JPA 예제는 같은 방법으로 `SqlCapture`가 잡은 실제 Hibernate SQL을 시뮬레이터 결과와 나란히 보여준다. 출력은 배포 워크플로가 테스트를 돌려 `/ci/<레슨>.json`으로 올린다. SQL을 직접 쳐 볼 만한 DB 레슨(인덱스·실행계획 등)은 브라우저용 PostgreSQL(PGlite)로 직접 실행하게 하고, 두 트랜잭션이 겹쳐야 하는 레슨(격리 수준, 락)은 PGlite가 연결 하나라 시뮬레이터를 쓴다. 검증 장에는 `<RunLocally>`로 테스트 파일 경로와 실행 명령을 넣는다. CheerpJ(브라우저 JVM)는 한국에서 로딩이 2분 가까이 걸려 쓰지 않는다(`spike/run-in-browser` 브랜치 기록).
