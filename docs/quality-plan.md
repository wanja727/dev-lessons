# 레슨 144개의 품질을 일정하게 관리하는 방법

**상태: 확정했다 (2026-11-23).** 진행 순서의 단계를 하나 끝낼 때마다, 거기서 정해진 규칙을 `docs/lesson-standard.md`와 `new-lesson` 스킬로 옮긴다.

로드맵(`docs/roadmap.md`)의 레슨은 144개다. 한 사람이 일일이 검수할 수 없는 양이다. 그래서 품질을 "잘 쓰려는 노력"이 아니라 틀, 자동 검사, 사전 승인으로 고정한다. 이 방식이 만드는 비용(AI 토큰)도 가장 적다.

## 지금 방식의 문제

레슨 세 개(N+1, 트랜잭션 기초, 커넥션 풀)를 새 구조로 쓰면서 드러난 것이다.

| 문제 | 무슨 일이 생기나 |
| --- | --- |
| 레슨마다 처음부터 짓는다 | 레슨 하나가 700줄쯤 되는 페이지다. 구조와 위젯 코드를 매번 다시 쓴다. 비용의 대부분이 여기서 나가고, 레슨마다 모양이 조금씩 달라진다 |
| 검사를 손으로 한다 | 화면을 띄워 폭과 넘침을 확인하는 일을 매번 반복한다. 비싸고 빠뜨릴 수 있다 |
| 방향이 틀린 것을 늦게 안다 | 다 쓴 뒤에 보고 고치면 쓴 만큼 버린다 |
| 대화가 길어질수록 비싸진다 | 한 대화에서 여러 레슨을 쓰면 뒤로 갈수록 한 번 답하는 비용이 커진다 |

## 방법

### 1. 레슨 유형마다 기준 레슨을 하나씩 먼저 만든다

지금 기준 레슨(`jpa-n-plus-1`)은 쿼리 수를 세는 유형 하나뿐이다. 로드맵에는 성격이 다른 유형이 넷 있다.

| 유형 | 과정 | 검증하는 방법 | 기준 레슨 |
| --- | --- | --- | --- |
| 동작 확인 | DB, 스프링, JPA, 시스템 설계 일부 | 실제로 돌려 나온 SQL과 결과 | 있다 (`jpa-n-plus-1`) |
| 자바 실행 | 자바 언어, 자료구조와 알고리즘, 동시성 | 코드를 돌린 실제 출력, 비교 횟수 | 없다 |
| 설계 | 객체지향 설계와 패턴, 아키텍처 | 요구를 바꿨을 때 고친 곳의 수 | 없다 |
| 개념 설명 | 네트워크와 웹, 운영체제, 테스트와 운영 | 테스트하기 어렵다. 공식 문서가 근거다 | 없다 |

- 유형마다 하나를 만들어 확인받고, 나머지는 그 틀을 따른다
- 설계 유형과 개념 설명 유형은 "답이 하나로 정해지는 문제"를 만들기가 어렵다. 이 계획에서 가장 불확실한 부분이라 맨 먼저 확인한다. 두 유형에서 레슨을 하나씩 골라, 페이지 없이 설계서와 문제만 먼저 써 본다
- 범위를 줄이는 기준: 핵심 질문에 판정 문제 2개를 채우지 못하면 그 질문을 뺀다. 남은 핵심 질문이 3개보다 적으면 그 레슨을 뺀다

### 2. 레슨을 글이 아니라 자료로 쓴다

핵심 질문, 결론, 근거 코드, 위젯 종류, 확인 문제를 정해진 칸에 채우면 페이지가 만들어지게 한다.

- 페이지 구조와 위젯 코드를 매번 쓰지 않는다. 레슨 하나를 쓰는 비용이 크게 준다
- 모든 레슨의 모양이 저절로 같아진다
- 자주 쓰는 위젯을 몇 가지 갖춰 두고 고른다. 후보: 한 단계씩 실행하기, 켜고 끄며 비교하기, 타임라인, 두 칸 비교, 상황 분류하기
- 잃는 것: 레슨마다 특별한 위젯을 만들 여지가 준다. 꼭 필요한 레슨은 예외로 직접 만든다
- 주의: 틀이 어설프면 모든 레슨이 어설퍼진다. 이미 쓴 레슨 세 개를 이 틀로 옮겨 보며 확인한다
- 이미 쓴 레슨 세 개는 모두 동작 확인 유형이다. 그것만 보고 만든 틀은 초안으로 둔다. 나머지 세 유형의 기준 레슨을 이 틀로 쓰면서 틀을 고치고, 네 유형이 모두 통과한 뒤에 틀을 굳힌다

이미 있는 것: 공통 모양(`site/src/styles/core-question.css`)과 공통 스크립트(`site/src/components/CoreQuestionKit.astro`). 예측, 확인 문제, 보지 않고 답하기, 진행 표시는 이미 공통이다. 남은 것은 페이지 뼈대와 위젯이다.

### 3. 규칙을 자동 검사로 옮긴다

레슨 표준의 규칙 가운데 기계가 볼 수 있는 것은 CI가 본다. 사람과 AI는 내용만 본다.

검사는 두 번에 나눠 만든다. 문제 파일 검사는 틀과 상관없어서 지금 만든다. 페이지 검사는 틀이 굳은 뒤에 만든다. 틀이 생기면 검사할 대상이 레슨 페이지에서 자료 파일과 위젯으로 바뀌기 때문이다.

| 검사 | 지금 | 대상 | 만드는 때 |
| --- | --- | --- | --- |
| 문제 파일의 형식 | CI에 있다 (`Check questions`) | `content/questions/*.yaml` | 있다 |
| 동작 주장 | CI에 있다 (`Verify lessons`) | `verification/` | 있다 |
| 가운뎃점 사용 | 손으로 한다 | 문제 파일, 뒤에 자료 파일 | 지금 |
| 핵심 질문마다 판정 문제 2개 이상, 설명형 1개 | 손으로 한다 | 문제 파일 | 지금 |
| 모든 문제가 핵심 질문에 묶여 있는지 | 주석으로만 적는다 | 문제 파일. 묶는 칸을 형식에 넣어야 한다 | 지금 |
| 해설이 굵은 결론으로 시작하는지 | 손으로 한다 | 문제 파일 | 지금 |
| 코드 한 줄의 길이 (44자, 접힌 영역 40자, 이은 줄 84자) | 손으로 한다 | 자료 파일 | 틀 다음 |
| 375px 폭에서 넘치지 않는지, 콘솔 오류가 없는지, 앱 안 화면 | 손으로 한다 | 위젯마다, 배포 전 사이트 | 틀 다음 |
| 출처 주소가 열리는지 | 손으로 한다 | 메타데이터, 문제 파일 | 지금. PR을 막지 않고 주기로 돈다 |

출처 주소 검사는 바깥 사이트의 사정으로 실패할 수 있어서 PR을 막는 검사에 넣지 않는다.

### 4. 쓰기 전에 설계서부터 승인받는다

레슨마다 반 쪽짜리 설계서를 먼저 만든다. 설계서는 따로 쓰는 문서가 아니라 2번 자료 파일의 앞부분이다. 아래 칸만 채운 자료 파일을 승인받고, 승인 뒤에 나머지 칸을 채운다.

- 핵심 질문 3~5개
- 질문마다 결론 한 문장
- 테스트로 확인할 주장 목록 (재료가 있으면 그 테스트의 어느 것인지)
- 질문마다 쓸 위젯의 종류
- 문제 개요 (질문마다 무엇을 물을지)
- 갖춰 둔 위젯으로 안 되는 레슨이면, 직접 만들 위젯과 그 이유

과정 하나의 설계서를 묶어서 한 번에 확인받는다. 읽는 데 레슨 하나에 1분쯤이다. 방향이 틀리면 여기서 고친다. 본문을 쓰기 전이라 버리는 것이 거의 없다. 품질의 대부분은 여기서 정해진다. 결론 문장이 맞으면 본문은 그것을 받치는 일이다.

### 5. 레슨 하나를 새 대화 하나에서 쓴다

- 승인된 설계서, 레슨 표준, 그 유형의 기준 레슨만 가지고 시작한다
- 대화가 짧아서 비용이 준다. 레슨마다 조건이 같아서 품질도 고르게 나온다
- PR은 레슨마다 main에서 따서 따로 연다

### 6. 다 만든 뒤에는 데이터로 고친다

학습 앱이 7일 뒤 정답률을 기록한다. 정답률이 낮은 문제와 레슨만 골라 고친다. 확신도는 문제를 풀 때마다 누르기 번거로워 앱과 레슨에서 없앴다 (2026-11-23). 전부를 미리 완벽하게 다듬지 않는다.

## 진행 순서

1. 문제 파일 형식에 "어느 핵심 질문의 문제인지" 칸을 넣는다. 형식은 Retrievo 저장소의 `docs/content-format.md`가 정한다
2. 문제 파일 자동 검사를 만든다 (3번의 "지금")
3. 설계 유형과 개념 설명 유형에서 레슨을 하나씩 골라 설계서와 문제만 써 본다. 안 되면 1번의 기준대로 범위를 줄인다
4. 자료를 채우면 페이지가 나오는 틀의 초안을 만들고, 이미 쓴 레슨 세 개를 옮긴다 (2번). 이때 든 비용을 적어 둔다
5. 나머지 유형의 기준 레슨 세 개를 틀로 쓰고, 틀을 굳힌다 (1번). 자바 실행, 설계, 개념 설명 유형 하나씩
6. 페이지 자동 검사를 만든다 (3번의 "틀 다음")
7. 첫 과정(자바 언어)의 설계서 묶음을 승인받고, 새 대화에서 레슨을 하나씩 쓴다 (4번, 5번)

1번에서 6번까지는 레슨을 거의 늘리지 않는 준비 작업이다. 여기에 쓴 비용은 뒤의 레슨에서 하나마다 돌려받는다.

## 아직 모르는 것

- 2번으로 비용이 얼마나 주는지는 해 보기 전에는 숫자로 말할 수 없다. 진행 순서 4번에서 레슨 세 개를 옮기며 잰다
- 설계 유형과 개념 설명 유형에서 답이 하나로 정해지는 문제를 충분히 만들 수 있는지. 진행 순서 3번에서 확인한다
- 레슨 목록 자체가 맞는지. 지금 목록은 면접에서 자주 나온다고 알려진 주제로 짠 후보다
