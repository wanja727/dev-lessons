# 틀 초안을 만들고 레슨 세 개를 옮겨 본 결과

품질 계획(`docs/quality-plan.md`) 4단계의 기록이다 (2026-11-23).

**결론: 자료 파일의 칸을 채우면 페이지가 나오는 틀이 동작한다.** 이미 쓴 레슨 세 개를 옮겼고, 옮긴 페이지는 원래 페이지와 글자, 눌렀을 때의 동작, 화면 높이가 같다. 레슨 하나에 써야 하는 분량은 22~34% 줄었다. 기대한 만큼 크게 줄지는 않았는데, 위젯의 절반 넘게가 공통 위젯으로 바뀌지 않았기 때문이다.

형식은 `docs/lesson-data-format.md`에 있다.

원래 페이지와 새 틀로 그린 페이지를 같은 화면에 나란히 띄우고 기계로 비교했다.

| 글자 | 문단, 목록, 표, 버튼, 코드 블록의 글자를 순서대로 비교 | 세 레슨 모두 같다 (블록 264개, 281개, 200개) |

| 화면 높이 | 375px와 900px 폭에서 구역마다의 높이를 비교 | 같다. 가로로 넘치는 곳도 없다 |
| 빌드 | `astro build` | 34쪽이 만들어진다 |

다른 점 하나: `tx-basics` 질문 4에서 방식을 바꾸면 숨겨지는 한 줄 정리에, 원래 페이지는 앞의 글자가 남아 있고 새 페이지는 비운다. 숨겨진 상태라 화면에는 보이지 않는다.

PGlite(브라우저 안의 PostgreSQL)를 내려받아 SQL을 실행하는 것과 CI 출력을 불러오는 것은 비교에서 뺐다. 마크업과 스크립트를 그대로 옮긴 부분이다.

| --- | --- | --- | --- |
| JPA N+1 문제 | 12,092자 | 1,929자 | 1,454자 (1개) |

- **없어진 것:** 페이지 뼈대, 구역마다의 마크업, 페이지 스타일, 예측과 확인 문제와 보지 않고 답하기를 잇는 스크립트
- **그대로인 것:** 본문의 글이다. 레슨마다 1만 자쯤이고, 줄일 수 없는 내용이다
- **위젯이 가른다:** 공통 위젯 하나의 설정은 평균 1,250자, 전용 위젯 하나는 평균 3,200자다. 위젯을 모두 공통 위젯으로 쓴 레슨이라면 자료 파일만 남아서 원래의 40~55%가 된다

토큰으로 센 비용은 적지 못했다. 이 작업에서 쓴 토큰 수를 내가 볼 수 없다. 그리고 레슨 세 개는 다시 쓴 것이 아니라 변환 스크립트로 옮겼기 때문에, 이번에 든 비용은 "레슨 하나를 새로 쓰는 비용"이 아니다. 그 숫자는 5번에서 기준 레슨 세 개를 이 형식으로 처음부터 쓸 때 잰다.

## 배운 것

1. **공통 위젯으로 바뀌는 것은 "경우를 고르면 정해진 장면이 나오는" 위젯이다.** 고를 수 있는 경우가 몇 개로 정해져 있으면 장면을 자료로 다 적을 수 있다. 슬라이더처럼 값이 이어지거나, 사용자가 누르는 순서에 따라 상태가 달라지면 계산하는 코드가 있어야 한다
2. **이미 쓴 레슨의 위젯은 계획이 본 것보다 손이 많이 간 것이었다.** 계획은 "꼭 필요한 레슨은 예외로 직접 만든다"고 했는데, 세 레슨에서는 절반 넘게가 예외였다. 3단계에서 써 본 설계서 둘은 질문 아홉 개를 모두 공통 위젯으로 채웠다. 설계서를 쓸 때 공통 위젯에서 먼저 고르면 예외는 줄어든다
3. **전용 위젯을 공통 위젯으로 바꾸면 레슨이 덜 좋아진다.** 슬라이더로 팀 수를 바꿔 보는 것을 "팀 3개일 때와 10개일 때" 두 경우로 줄일 수는 있지만 직접 해 보는 맛이 준다. 이번에는 하나도 줄이지 않았다. 어디까지 줄일지는 레슨마다 설계서에서 정한다
4. **모양이 같아지는 것은 틀이 보장한다.** 구역의 순서, 결론 상자, 확인 문제, 보지 않고 답하기는 자료 파일에서 바꿀 수 없다. 빠진 칸이 있으면 빌드가 실패한다
5. **오래 켜 둔 개발 서버는 옛 스타일을 내놓기도 한다.** 비교하다가 원래 페이지의 높이가 다르게 나왔는데, 서버를 다시 켜니 같아졌다. 화면을 확인하기 전에 서버를 다시 켠다
