# 설계 유형과 개념 설명 유형이 되는지 써 본 결과

품질 계획(`docs/quality-plan.md`) 3단계의 기록이다 (2026-11-23).

**결론: 두 유형 모두 된다.** 레슨을 하나씩 골라 설계서와 문제를 써 보니, 핵심 질문마다 답이 하나로 정해지는 판정 문제가 3개 이상 나왔다. 범위를 줄이는 기준에 걸린 핵심 질문은 없다.

다만 유형마다 레슨 하나만 써 본 것이다. 아래 "위험이 남은 레슨"은 설계서를 쓸 때 먼저 확인한다.

## 써 본 것

| 유형 | 레슨 | 설계서 | 문제 |
| --- | --- | --- | --- |
| 설계 | O3 단일 책임과 개방 폐쇄 원칙 | `srp-ocp.md` | `srp-ocp.yaml` |
| 개념 설명 | N7 쿠키, 세션, 토큰 | `cookie-session-token.md` | `cookie-session-token.yaml` |

- 쉬운 레슨을 고르지 않았다. O3은 의견이 갈리기 쉬운 원칙 이야기이고, N7은 "세션과 토큰 가운데 무엇이 좋은가"로 흐르기 쉬운 주제다
- 페이지는 쓰지 않았다. 설계서의 "질문마다 본문이 말할 것"을 본문 대신 근거로 삼았다
- 문제는 모두 `status: draft`다. `content/questions`에 두지 않아서 학습 앱이 가져가지 않는다. 레슨을 쓸 때 옮긴다
- 두 문제 파일은 Retrievo의 형식 검사와 `scripts/check-questions.mjs`를 오류 없이 통과한다

## 기준에 대 본 결과

기준: 핵심 질문에 판정 문제 2개를 채우지 못하면 그 질문을 뺀다. 남은 핵심 질문이 3개보다 적으면 그 레슨을 뺀다.

| 레슨 | 핵심 질문 | 판정 | 설명형 | 뺀 질문 |
| --- | --- | --- | --- | --- |
| 단일 책임과 개방 폐쇄 원칙 | 5개 | 17개 (질문마다 3~4개) | 6개 | 없음 |
| 쿠키, 세션, 토큰 | 4개 | 18개 (질문마다 4~5개) | 5개 | 없음 |

판정 문제 35개의 모양을 나누면 이렇다.

| 모양 | 설계 | 개념 설명 | 예 |
| --- | --- | --- | --- |
| 조건을 주고 무슨 일이 일어나는지 묻는다 | 13개 | 13개 | "SILVER 주문 10,000원을 넣으면 무엇이 나오나", "계정을 정지한 뒤 이 토큰으로 온 요청은 어떻게 되나" |
| 정의나 용어를 묻는다 | 4개 | 5개 | "수정에 닫혀 있다는 무슨 뜻인가", "쿠키를 저장하게 하는 헤더는" |

정의를 묻는 문제만으로 채워지지 않았다. 네 개 가운데 세 개가 조건을 주고 결과를 묻는 문제다.

## 답이 하나로 정해지는 문제의 모양

### 설계 유형

- **고칠 곳 고르기:** 코드와 요구를 주고 "고쳐야 하는 클래스는", "고쳐야 하는 줄은", "고치지 않아도 되는 것은"을 묻는다
- **고칠 곳 세기:** "컴파일되려면 파일을 몇 개 고쳐야 하나"
- **코드를 돌린 결과:** "고치는 것을 빠뜨리면 무엇이 나오나", "이 코드를 컴파일하면 어떻게 되나"
- **흔한 오해:** "메서드가 하나여야 한다는 뜻이다 (X)"

쓰지 않은 모양: "이 코드는 좋은 설계인가", "어느 쪽이 더 나은가", "이 원칙을 언제 적용해야 하나". 답이 사람마다 다르다.

질문 5는 처음에 "두 원칙은 언제 적용하나요?"로 잡았다가 바꿨다. 판정 문제를 만들 수 없었기 때문이다. "개방 폐쇄 원칙을 지키면 어떤 변경이든 고치지 않고 할 수 있나요?"로 바꾸니 고칠 파일 수와 컴파일 결과로 물을 수 있었다. 언제 적용하는지는 그 답에서 따라 나온다.

### 개념 설명 유형

- **조건을 정한 상황:** 서버 수, 저장소를 함께 쓰는지, 만료 시간, 서버가 무엇을 확인하는지를 문제에 적고 "이 요청은 어떻게 되나"를 묻는다
- **요청과 응답 읽기:** 헤더를 보여 주고 다음 요청의 헤더나 서버의 처리를 묻는다
- **용어:** 헤더 이름, 구성 순서. 표준 문서에 답이 있다

쓰지 않은 모양: "세션과 토큰 가운데 무엇을 써야 하나", "JWT는 안전한가". 조건이 없으면 답이 정해지지 않는다.

## 배운 것

계획과 틀(진행 순서 4번)에 반영할 것들이다.

1. **설계서에 "질문마다 본문이 말할 것" 칸이 필요하다.** 계획의 설계서 목록에는 없던 칸이다. 문제를 쓸 때 "레슨에 근거가 있는가"를 이 칸에 대 보고 확인했다. 결론 한 문장만으로는 문제 10여 개의 근거가 되지 않는다
2. **개념 설명 유형도 주장의 대부분을 테스트로 확인할 수 있다.** 계획의 유형 표는 "테스트하기 어렵다. 공식 문서가 근거다"라고 적었는데, 쿠키와 세션과 토큰 레슨의 주장 일곱 가운데 일곱 모두 스프링 부트 테스트나 자바 코드로 확인할 수 있다. 문서가 근거인 것은 용어의 정의뿐이다
3. **설계 유형의 검증 방법이 정해졌다.** 요구를 반영하기 전과 후의 코드를 패키지 둘에 나란히 두고 테스트가 파일을 비교한다. 컴파일 오류는 테스트 안에서 자바 컴파일러를 불러 확인한다. 아직 만들지는 않았다
4. **갖춰 둘 위젯 다섯 가지로 두 레슨의 질문 아홉 개를 모두 채웠다.** 두 칸 비교 3번, 한 단계씩 실행하기 3번, 상황 분류하기 2번, 타임라인 1번. 켜고 끄며 비교하기는 한 단계씩 실행하기 안의 스위치로 한 번 썼다. 따로 만들 위젯은 없었다
5. **코드가 없는 레슨은 요청과 응답의 모양이 코드 자리를 채운다.** 틀의 "근거 코드" 칸은 자바 코드만이 아니라 HTTP 메시지 같은 글 덩어리도 받아야 한다
6. **"언제 무엇을 쓰나"를 묻는 질문은 "이 조건에서 무슨 일이 일어나나"로 바꿔 쓴다.** 고르는 기준은 그 답에서 따라 나오게 하고, 설명형 문제의 체크리스트에 담는다

## 위험이 남은 레슨

써 보지 않고 로드맵의 제목과 "다루는 것"만 보고 판단한 것이다. 고르는 기준이나 장단점이 주제인 레슨들이다. 과정을 시작해 설계서를 쓸 때 이 레슨들부터 본다.

| 레슨 | 걱정되는 점 | 써 볼 방향 |
| --- | --- | --- |
| A9 모놀리스와 마이크로서비스 | 얻는 것과 잃는 것이 주제다. 돌려 볼 코드가 없다 | 조건을 정한 상황(서비스 하나가 죽었을 때, 한 요청이 서비스 셋을 거칠 때)으로 묻는다 |
| D12 관계형 DB와 NoSQL | "언제 무엇을 고르나"가 주제다 | 같은 데이터를 두 방식으로 담았을 때 되는 조회와 안 되는 조회로 묻는다 |
| A2 도메인 모델과 트랜잭션 스크립트 | 설계 취향이 갈린다 | 설계 유형처럼 요구를 바꿨을 때 고칠 곳으로 묻는다 |
| T6 CI/CD와 무중단 배포 | 도구와 방식이 여럿이다 | 배포 도중의 한 시점을 정해 "지금 어느 버전이 요청을 받나"로 묻는다 |
| O1 객체지향의 네 가지 특징 | 정의를 외우는 레슨이 되기 쉽다 | 코드를 주고 어느 특징을 어겼는지, 고치면 무엇이 달라지는지로 묻는다 |
| N2 OSI 7계층과 TCP/IP 4계층 | 분류를 외우는 문제만 나오기 쉽다 | 답은 하나로 정해지지만 조건을 주고 결과를 묻는 문제가 적을 수 있다. 판정 문제 수는 채워질 것으로 본다 |
