# 설계서: 쿠키, 세션, 토큰

품질 계획 3단계에서 **개념 설명 유형**이 되는지 보려고 쓴 설계서다. 본문은 아직 쓰지 않았다. 문제는 `cookie-session-token.yaml`에 있다.

| 항목 | 내용 |
| --- | --- |
| 로드맵 | N7. 네트워크와 웹 |
| 유형 | 개념 설명 |
| 선수 | N4 HTTP 요청과 응답 |
| 전제 | 요청과 응답에 헤더가 있다는 것을 안다. JWT는 서명만 한 형태를 다룬다 (암호화한 JWT는 다루지 않는다) |
| 예제 | 사용자 kim이 쇼핑몰에 로그인하고 내 정보(`GET /me`)를 본다 |

## 레슨 전체에서 쓰는 상황

코드 대신 요청과 응답의 헤더를 보여 준다. 문제도 같은 모양으로 쓴다.

**쿠키가 오가는 모양**

```
HTTP/1.1 200 OK
Set-Cookie: theme=dark
```

```
GET /me HTTP/1.1
Cookie: theme=dark
```

**세션 방식.** 서버의 세션 저장소에 `abc123 → kim`이 들어 있고, 브라우저는 번호만 보낸다.

```
GET /me HTTP/1.1
Cookie: JSESSIONID=abc123
```

**토큰(JWT) 방식.** 토큰은 점으로 나뉜 세 부분(헤더, 페이로드, 서명)이다. 페이로드에는 `{"sub":"kim","role":"USER"}`가 들어 있다.

```
GET /me HTTP/1.1
Authorization: Bearer eyJhbGci...
```

## 먼저 예측해 보기

"서버 A와 B가 세션을 각자 자기 메모리에만 저장해요. A에서 로그인한 사용자의 다음 요청이 B로 가면 어떻게 될까요?" 답은 "로그인하지 않은 요청으로 처리된다"이고 질문 2에서 확인한다.

## 핵심 질문과 결론

| | 질문 | 결론 (첫 줄) | 받치는 문장 (둘째 줄) |
| --- | --- | --- | --- |
| q1 | 쿠키는 무엇이고 왜 필요한가요? | 서버가 준 값을 브라우저가 저장했다가 요청마다 자동으로 실어 보내는 것이에요. | HTTP는 요청을 따로따로 이해해서, 요청마다 "나는 누구"를 알려 주는 값이 함께 가야 해요. |
| q2 | 세션 방식은 어떻게 로그인 상태를 유지하나요? | 로그인 정보는 서버가 저장하고, 브라우저에는 그 정보를 찾는 번호(세션 ID)만 쿠키로 줘요. | 서버는 요청마다 세션 ID로 저장소에서 로그인 정보를 찾아요. |
| q3 | 토큰(JWT) 방식은 어떻게 다른가요? | 로그인 정보를 서명한 토큰에 담아 클라이언트에 주고, 서버는 저장하지 않아요. | 서버는 요청마다 서명과 만료 시간만 확인해요. 내용을 바꾸면 서명이 맞지 않아요. |
| q4 | 두 방식은 각각 무엇을 얻고 무엇을 잃나요? | 세션은 서버가 바로 끊을 수 있지만 서버들이 저장소를 함께 써야 하고, JWT는 저장소가 필요 없지만 만료 전에는 막기 어려워요. | 그래서 JWT는 만료 시간을 짧게 잡아요. |

질문은 앞 질문의 답에서 나온다: 값을 실어 보내는 수단(q1) → 그 값으로 번호를 보내는 방식(q2) → 번호 대신 정보 자체를 보내는 방식(q3) → 둘의 차이(q4).

"어느 쪽이 더 좋은가"는 묻지 않는다. 조건을 정해 주고 "이때 무슨 일이 일어나나"를 묻는다.

## 질문마다 본문이 말할 것

문제는 여기에 적은 것만 묻는다.

### q1. 쿠키는 무엇이고 왜 필요한가요?

- HTTP는 무상태다. 요청 하나하나를 앞의 요청과 상관없이 따로 이해할 수 있게 되어 있다. 서버는 이 요청이 아까 그 사람의 요청인지 HTTP만으로는 알 수 없다
- 그래서 요청마다 누구인지 알려 주는 값을 함께 보내야 한다
- 서버는 응답의 `Set-Cookie` 헤더로 값을 준다. 브라우저는 저장했다가 그 사이트로 가는 요청의 `Cookie` 헤더에 자동으로 넣는다. 페이지의 자바스크립트가 넣어 주는 것이 아니다
- 쿠키는 브라우저에 저장된다. 사용자가 개발자 도구로 보거나 바꿀 수 있다. 그래서 `role=ADMIN` 같은 값을 그대로 담으면 안 된다
- **위젯: 타임라인.** 로그인 요청, `Set-Cookie`가 든 응답, `Cookie`가 든 다음 요청을 차례로 넘기며 헤더가 생기는 곳을 본다

### q2. 세션 방식은 어떻게 로그인 상태를 유지하나요?

- 로그인하면 서버는 로그인 정보(누구인지, 권한)를 서버 쪽 저장소에 저장하고, 그 정보를 찾는 번호인 세션 ID를 만든다
- 서버는 세션 ID를 `Set-Cookie`로 준다. 스프링 부트(톰캣)에서 쿠키 이름은 `JSESSIONID`다
- 쿠키에는 세션 ID만 있다. 사용자 이름이나 권한은 서버에 있다
- 다음 요청이 오면 서버는 쿠키의 세션 ID로 저장소에서 로그인 정보를 찾는다
- 서버가 세션을 지우면(로그아웃) 브라우저에 쿠키가 남아 있어도 그 세션 ID로는 찾을 정보가 없다. 로그인하지 않은 요청이 된다
- 서버가 두 대이고 세션을 각자 메모리에 저장하면, A에서 로그인한 사용자의 요청이 B로 갔을 때 B에는 그 세션이 없다. 서버들이 세션 저장소를 함께 써야 한다
- **위젯: 한 단계씩 실행하기.** 로그인부터 다음 요청까지 한 단계씩 넘기며 세션 저장소와 브라우저 쿠키에 무엇이 들어가는지 본다. "서버 2대" 스위치를 켜면 요청이 B로 가서 세션을 찾지 못한다

### q3. 토큰(JWT) 방식은 어떻게 다른가요?

- 로그인하면 서버는 로그인 정보를 담은 토큰을 만들어 클라이언트에 준다. 서버는 저장하지 않는다
- JWT는 점으로 나뉜 세 부분이다: 헤더, 페이로드, 서명. 페이로드에 사용자 정보와 만료 시간이 들어간다
- 서명은 서버만 아는 키로 헤더와 페이로드를 계산해 만든다
- 서버는 요청마다 서명이 맞는지와 만료 시간이 지났는지만 확인한다. 저장소에서 찾아보지 않는다
- 페이로드를 바꾸면 서명이 맞지 않아 서버가 거부한다
- 페이로드는 암호화된 것이 아니다. 인코딩만 되어 있어서 토큰을 가진 사람은 누구나 읽을 수 있다. 비밀번호 같은 것을 넣지 않는다
- 토큰은 보통 `Authorization: Bearer 토큰` 헤더로 보낸다
- **위젯: 한 단계씩 실행하기.** 토큰의 세 부분을 색으로 나눠 보여 주고, 페이로드의 `role`을 `ADMIN`으로 바꾸면 서명 확인이 실패하는 것을 본다

### q4. 두 방식은 각각 무엇을 얻고 무엇을 잃나요?

- 세션: 서버가 세션을 지우면 바로 로그인이 끊긴다. 대신 서버가 여러 대면 세션 저장소를 함께 써야 하고, 요청마다 저장소를 찾아본다
- JWT: 서버가 저장하지 않는다. 같은 서명 키를 가진 서버는 어느 서버든 토큰을 확인할 수 있다
- JWT는 만료 전에는 막기 어렵다. 서버가 서명과 만료 시간만 확인하면, 계정을 정지해도 그 토큰은 만료될 때까지 통과한다
- 서버가 토큰의 `role`만 보고 권한을 판단하면, DB에서 권한을 바꿔도 이미 준 토큰에는 옛 권한이 적혀 있다
- 만료 전의 토큰을 막으려면 막을 토큰을 서버에 저장해 두고 요청마다 확인해야 한다. 저장소가 다시 필요해진다
- 그래서 JWT는 만료 시간을 짧게 잡는다
- **위젯: 두 칸 비교.** "계정 정지" 버튼을 누른 뒤 다음 요청이 세션 방식과 JWT 방식에서 각각 어떻게 처리되는지 나란히 본다

## 테스트로 확인할 주장

개념 설명 유형은 "테스트하기 어렵다. 공식 문서가 근거다"로 분류했는데, 이 레슨은 주장의 대부분을 테스트로 확인할 수 있다.

| 주장 | 확인하는 방법 |
| --- | --- |
| 로그인 응답에 `Set-Cookie: JSESSIONID=...`가 있고, 쿠키 값에 사용자 이름이 없다 | 스프링 부트 테스트로 로그인 요청을 보내 응답 헤더를 본다 |
| 세션 ID 쿠키를 보내면 로그인된 요청으로 처리된다. 세션을 지우면 같은 쿠키가 거부된다 | 같은 테스트에서 세션을 지우기 전과 뒤에 요청한다 |
| 세션 저장소가 다른 서버에서는 세션 ID를 찾지 못한다 | 애플리케이션을 둘 띄워 한쪽에서 받은 쿠키를 다른 쪽에 보낸다 |
| JWT는 점으로 나뉜 세 부분이고, 페이로드는 키 없이 읽을 수 있다 | 토큰을 만들어 가운데 부분을 디코딩한다 |
| 페이로드를 바꾸면 서명 확인이 실패한다 | 페이로드만 바꾼 토큰을 확인한다 |
| 같은 서명 키를 가진 다른 서버가 토큰을 통과시킨다 | 애플리케이션을 둘 띄워 한쪽에서 받은 토큰을 다른 쪽에 보낸다 |
| 계정을 정지해도 만료 전의 토큰은 통과한다 (서명과 만료 시간만 확인할 때) | 계정 상태를 바꾼 뒤 같은 토큰으로 요청한다 |

JWT의 세 부분, 키 없이 읽히는 페이로드, 바꾼 페이로드의 서명 실패는 이 설계서를 쓰면서 자바 21로 직접 돌려 확인했다. 나머지 테스트는 아직 만들지 않았다. 기준 레슨을 쓸 때(진행 순서 5번) 만든다.

테스트로 확인할 수 없는 것은 용어의 정의다(무상태, 헤더 이름). 표준 문서를 근거로 단다.
